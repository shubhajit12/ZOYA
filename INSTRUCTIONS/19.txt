# CURRENT PROBLEM

The current architecture uses:

* OrbitControls for orbit/pan
* custom velocity-based camera/target dolly for zoom

The custom zoom is currently broken.

When the user scrolls to zoom in or out, the model can completely disappear from view.

Do NOT attempt another sensitivity/friction/pivot-tuning patch to the existing custom camera-dolly system.

The fundamental requirement is:

> OrbitControls must remain the single owner of camera navigation state.

The custom per-frame camera/target dolly must be removed.

---

# REQUIRED FINAL ARCHITECTURE

Use ONE navigation controller:

**OrbitControls owns:**

* orbit
* pan
* zoom
* camera position
* controls.target
* navigation state
* damping/inertia

There must be NO second camera-navigation controller fighting OrbitControls.

There must be NO custom per-frame camera/target dolly.

There must be NO code that independently moves the camera and controls.target for wheel zoom.

There must be exactly ONE:

`controls.update()`

per animation frame.

# 3. WHEEL ZOOM — ORBITCONTROLS NATIVE

THIS IS THE MOST IMPORTANT CHANGE.

Remove the custom velocity-based wheel zoom implementation.

Do NOT use:

* zoomVelocity
* pending zoom queues
* zoomTargetCam
* zoomTargetLook
* custom exponential camera dolly
* custom per-frame camera movement
* custom per-frame target movement
* custom camera scaling around a pivot
* `C' = P + s(C-P)`
* `T' = P + s(T-P)`

The wheel should instead use OrbitControls' native zoom/dolly mechanism.

Set:

`enableZoom = true`

and allow OrbitControls to process the wheel event itself.

Use OrbitControls' native:

* dollyIn()
* dollyOut()
* zoomToCursor

capability if supported by the installed Three.js r185 OrbitControls implementation.

Before changing anything, inspect the actual installed OrbitControls source in:

`node_modules/three/examples/jsm/controls/OrbitControls.js`

Confirm the exact r185 API/behavior rather than assuming it.
